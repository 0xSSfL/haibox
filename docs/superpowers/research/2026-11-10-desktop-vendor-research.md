# HAIBOX Desktop vendor research

**Checked:** 2026-11-10 (UTC)  
**Scope:** Official Docker/Moby, KasmVNC, noVNC, Xpra, Waypipe, Exegol, Fedora Packages, and PortSwigger material. This is source research for a design proposal, not an architecture decision or legal opinion.

## Docker isolated bridge and a local browser relay

- Docker's `isolated` bridge gateway mode is only valid with an internal network. It leaves the bridge without a host-side IP address. The Moby change that introduced the mode describes this as removing the host's address/route into the network; a Moby maintainer later clarified that it blocks host access by container IP on Linux. [Docker port-publishing docs](https://docs.docker.com/engine/network/port-publishing/) · [Moby PR #49262](https://github.com/moby/moby/pull/49262) · [Moby issue #49680](https://github.com/moby/moby/issues/49680)
- Docker documents that internal networks have no default route for external connectivity and can communicate among their attached containers. An internal-only container has no default-gateway network through which Docker can publish a host port: a Moby maintainer confirmed that a requested mapping may be accepted but remain unpublished until a non-internal network is attached. The `isolated` gateway setting additionally removes the normal host-side bridge address. [Docker `network create` docs](https://docs.docker.com/reference/cli/docker/network/create/) · [Moby maintainer discussion #53256](https://github.com/moby/moby/discussions/53256)
- On a normal bridge, Docker supports `-p 127.0.0.1:HOST:CONTAINER` to bind a published port to the Docker host's loopback address. That behavior should not be assumed for a container attached only to an internal/isolated network; Docker/Moby's explanation above says it has no gateway network for port publication. [Docker port-publishing docs](https://docs.docker.com/engine/network/port-publishing/)
- Docker Engine's exec API can create a command attached to stdin/stdout/stderr and start it non-detached as an interactive session. Docker's attached-stream documentation describes a bidirectional Engine connection; non-TTY output is multiplexed, while TTY output is a raw PTY stream. The API does not define a browser WebSocket endpoint for `exec` (the separate container `attach/ws` endpoint attaches the container's primary process). [Docker Engine API v1.56](https://docs.docker.com/reference/api/engine/version/v1.56/)

**Transport inference:** A host-side process can terminate a browser's `ws://127.0.0.1:...` connection and bridge application bytes to/from a long-running `docker exec` process over attached stdio. A generic browser-style WebSocket upgrade and masked text-frame echo passed through a test relay, but that did not test KasmVNC rendering or browser authentication. The Engine stream is not itself the browser's WebSocket: the host process must implement the WebSocket handshake, map data in both directions, handle Docker stream framing/TTY behavior, and manage backpressure and process lifetime. The host relay also needs Docker Engine API access; stdio does not remove that control-plane trust boundary.

## Xpra, native windows, and Wayland forwarding

- **Seamless mode:** Xpra forwards selected application windows as native windows managed by the local OS/window manager. The application session remains running after disconnect and can be reattached. The HTML5 client keeps windows inside a browser page; Xpra documents its regular native client for windows integrated with the desktop. [Xpra seamless-mode guide](https://github.com/Xpra-org/xpra/blob/master/docs/Usage/Seamless.md)
- **Session and feature controls:** Sessions can be started with specific children and reconnected by SSH/display or session name. Lifecycle options include ending the server when launched children exit, when no forwarded windows remain, or when the last client disconnects. Xpra exposes separate forwarding controls for clipboard, audio, printers, webcams, file transfers, tray, and notifications; its security guide recommends disabling unused subsystems and says `start-new-commands` permits remote command execution and should be disabled for untrusted clients. [Seamless-mode guide](https://github.com/Xpra-org/xpra/blob/master/docs/Usage/Seamless.md) · [Manual](https://xpra.org/manual) · [Feature catalog](https://github.com/Xpra-org/xpra/blob/master/docs/Features/README.md) · [Security guide](https://github.com/Xpra-org/xpra/blob/master/docs/Usage/Security.md)
- **Authentication and transports:** Xpra supports local sockets, SSH, TCP, TLS, WebSocket, and secure WebSocket. Its current network guide describes SSH as providing host verification, authentication, and encryption; plain TCP/WebSocket are unencrypted. Authentication can be configured per listener (for example a password file), and should be paired with an encrypted transport when crossing a trust boundary. [Xpra networking](https://github.com/Xpra-org/xpra/blob/master/docs/Network/README.md) · [Authentication](https://github.com/Xpra-org/xpra/blob/master/docs/Usage/Authentication.md)
- **Exegol UX reference only:** Exegol's `--gui` shares the host's X11 or Wayland GUI so individual container apps appear in the host desktop; it is enabled by default in the documented CLI. Its `--desktop` option is a separate full desktop, available through a web interface by default or VNC. These docs illustrate two different user experiences, not an isolation model for HAIBOX. [Exegol `start` options](https://docs.exegol.com/wrapper/cli/start) · [Exegol profile reference](https://docs.exegol.com/wrapper/profiles/reference)
- **Fedora packages and dependencies:** Fedora's package index lists the `xpra` package plus a separate `xpra-client-gtk3` package. As checked, Fedora 45 had Xpra `6.5.4-1.fc45`; the server package's direct requirements included GStreamer, PipeWire, systemd libraries, Xorg server, and Xpra runtime components. The GTK3 package depends on the matching `xpra` build. The upstream Xpra packaging guide describes a finer package split (`xpra-server`, `xpra-server-wayland`, `xpra-x11`, audio/codecs, and GTK client), so package names and the installed dependency closure should be taken from Fedora's target release rather than copied from upstream packaging docs. [Fedora `xpra` Fedora 45 build](https://packages.fedoraproject.org/pkgs/xpra/xpra/fedora-45-updates.html) · [Fedora GTK3 client Fedora 45 build](https://packages.fedoraproject.org/pkgs/xpra/xpra-client-gtk3/fedora-45-updates.html) · [Fedora Xpra package index](https://packages.fedoraproject.org/pkgs/xpra/) · [Xpra upstream packaging](https://github.com/Xpra-org/xpra/blob/master/docs/Build/Packaging.md)
- **Wayland alternatives:** Waypipe is a proxy for Wayland clients, aiming for `ssh -X`-style application forwarding. Its upstream man page documents `waypipe ssh` running client/server halves and forwarding Wayland apps; the server half acts as a compositor for the remote apps. The Wayland project FAQ says Waypipe works with all Wayland compositors. Xpra also has a Wayland seamless backend, but Xpra describes it as experimental and potentially requiring `xpra-server-wayland`. Waypipe's own security section warns it provides no strong security guarantees and does not filter all Wayland protocols. [Waypipe upstream man page](https://gitlab.freedesktop.org/mstoeckl/waypipe/-/raw/master/waypipe.scd) · [Wayland FAQ](https://wayland.freedesktop.org/faq) · [Xpra Wayland backend notes](https://github.com/Xpra-org/xpra/blob/master/docs/Usage/Seamless.md) · [Xpra package split](https://github.com/Xpra-org/xpra/blob/master/docs/Build/Packaging.md)

**Xpra stream compatibility: confirmed facts and inference**

- **Confirmed:** Xpra documents SSH, TCP, TLS, WebSocket, and local-socket transports. Xpra-org's `go-xpra` documents SSH by launching remote `xpra _proxy [display]`, and explicitly states that stdin carries the Xpra protocol; the Xpra-org Rust client describes SSH subprocess stdin/stdout pipes as the Xpra byte stream and says this is the mechanism used by Xpra's own client. [Xpra networking](https://github.com/Xpra-org/xpra/blob/master/docs/Network/README.md) · [Xpra Go client](https://github.com/Xpra-org/go-xpra/blob/main/README.md) · [Xpra Rust client](https://github.com/Xpra-org/rust-xpra)
- **Inference, not a documented Docker integration:** Xpra does not provide a turnkey Docker Exec transport. The isolated PoC in [`2026-11-10-xpra-seamless.md`](../poc/2026-11-10-xpra-seamless.md) did verify Xpra 6.5.4 client/server traffic through a no-TTY Docker Exec stdio relay and rendered xterm windows in a Fedora 44 X11 session. This establishes one working protocol/version/host combination, not a supported `stdio://` URI, production relay, cross-distro behavior, or Wayland support. The Xpra Go client README checked here requires an Xpra 7.0+ server; that separate client was not used in the PoC.

## KasmVNC and noVNC

- **noVNC** is a browser VNC client. It follows standard RFB and requires WebSocket support from its server; where a VNC server only exposes TCP, the noVNC project points to `websockify`, which terminates WebSockets and forwards the application stream to TCP. noVNC itself is not a desktop/VNC server. [noVNC README](https://github.com/novnc/noVNC/blob/master/README.md) · [websockify README](https://github.com/novnc/websockify)
- **KasmVNC** is a browser-oriented remote desktop server plus web client. Its server has a built-in web server and sends desktop rendering over WebSockets by default; its documentation also describes WebRTC UDP as an experimental/conditional transport. KasmVNC intentionally diverges from RFB and does not support legacy VNC viewer apps. Its web front end is a Kasm-maintained noVNC fork, modified for KasmVNC, and is bundled with the server. [KasmVNC server docs](https://docs.kasmvnc.com/docs/developer/serverside/) · [KasmVNC project README](https://github.com/kasmtech/KasmVNC/blob/master/README.md) · [Kasm-maintained noVNC fork](https://github.com/kasmtech/noVNC)
- The current KasmVNC configuration reference allows setting `network.interface` to a specific listen address and `network.udp.public_ip` to `127.0.0.1` to disable WebRTC UDP; the reverse-proxy guide demonstrates `network.interface: 127.0.0.1`. That supports a design where KasmVNC itself listens only on the GUI container's loopback and the CLI tunnel is the only path to it. [Configuration](https://docs.kasmvnc.com/docs/configuration/) · [Reverse proxy guide](https://docs.kasmvnc.com/how-to/reverse_proxy/)
- **License note:** The KasmVNC repository identifies its license as GPL-2.0; upstream noVNC describes its core as MPL-2.0, with separate licenses for some bundled assets. Check the exact KasmVNC release and included components before redistribution. [KasmVNC license](https://github.com/kasmtech/KasmVNC/blob/master/LICENSE.TXT) · [noVNC license](https://github.com/novnc/noVNC/blob/master/LICENSE.txt)

## HAIBOX isolated-network transport probe

- On 2026-11-10, the local dedicated Docker context reported Engine 29.9.2. A temporary engagement was created through HAIBOX with the existing Core image and the normal isolated network profile. Inspection showed `Internal=true`, both IPv4 and IPv6 gateway modes set to `isolated`, no bridge gateway address, no published-port bindings, UID/GID `1000:1000`, a read-only root filesystem, `CapDrop=["ALL"]`, and only the workspace (read/write) and scope file (read-only) mounted.
- `ip route` inside that runner showed only its connected engagement subnet and no default route. A host-side test relay bound to `127.0.0.1` successfully carried a browser-style WebSocket HTTP upgrade and a masked text-frame echo through `docker exec --interactive` (without a TTY) to a mock service bound to `127.0.0.1` inside the container. No port publishing was used.
- This verifies the Docker exec byte-stream transport over the current isolated network. It does **not** verify KasmVNC, a real browser rendering a desktop, relay authentication, or host-service negative probes. Existing [HAIBOX verification status](../../verification-status.md) records a prior manual isolated-profile probe in which host LAN SSH/PostgreSQL, host bridges, public IPv4/IPv6, external DNS, and metadata were unreachable.
- The disposable engagement, container, and network were removed using `haibox engagement destroy --force --yes`; subsequent Docker inspections confirmed the container and network were absent. The test changed no daemon settings or firewall rules. One initial harness run timed out because its test-only HTTP delimiter was incorrectly escaped; the corrected harness passed.
